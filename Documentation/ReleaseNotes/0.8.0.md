# swift-cidr 0.8.0

**Status: unreleased.** These notes describe the context-preserving migration
on the development branch. They do not announce a published version or tag.

## Address Traversal Preserves the Parent Prefix

`IPNetwork` retains its `Sequence` conformance. Every address it yields now
carries the network's prefix length, including its first and last addresses:

```swift
import CIDR

let network = IPv4Network("192.0.2.0/30")!
print(Array(network).map(\.description))
// ["192.0.2.0/30", "192.0.2.1/30", "192.0.2.2/30", "192.0.2.3/30"]

print(Array(network.addresses).map(\.description))
// The same four contextual addresses.
```

Previously, those elements carried `/32`; IPv6 iteration similarly replaced
the parent prefix with `/128`. This is an intentional behavioral change.
Address bits, traversal order, and the inclusion of boundary addresses are
unchanged. Each yielded address's `network` projection equals its parent.

The new `IPNetwork<Family>.Addresses` view makes address enumeration explicit.
It has a dedicated `Iterator` with independent cursor state. `IPNetwork` keeps
its existing `makeIterator() -> AnyIterator<Element>` signature and delegates
to the same traversal implementation. Neither `IPNetwork` nor `IPAddress`
becomes an `IteratorProtocol` cursor.

`subnets(prefixLength:)` continues to yield canonical networks at the requested
prefix length. RPSL selectors retain their existing prefix-selection meaning.

## Containment and Exact Membership

Use `contains(address:)` to ask whether the candidate's entire prefix context
fits within the network. The candidate must be at least as specific as the
container and its address bits must fall inside the container. For example,
`192.0.2.1/24` is not contained by `192.0.2.0/30`.

Use `contains(subnet:)` to check complete containment of another canonical
prefix. An equal network is contained; a broader prefix or an adjacent network
is not. `AnyIPNetwork` provides the corresponding named operations and returns
`false` for a different address family.

Use `network.addresses.contains(candidate)` for exact membership among the
values that iteration yields. `IPAddress` equality compares both address bits
and prefix length, so the candidate must have the parent's prefix length.

For `network = 192.0.2.0/30`:

| Candidate | `contains(address:)` | `addresses.contains(_:)` | Deprecated direct `contains(_:)` |
| --- | --- | --- | --- |
| `192.0.2.1/24` | false | false | true |
| `192.0.2.1/30` | true | true | true |
| `192.0.2.1/31` | true | false | true |
| `192.0.2.1/32` | true | false | true |
| `192.0.2.4/30` | false | false | false |

The existing unlabeled address overload is deprecated but retains its raw-bit
containment behavior. The candidate's prefix length is still ignored. The unlabeled
subnet overload retains its existing complete-prefix containment behavior and
is deprecated in favor of `contains(subnet:)`. Review the desired meaning when
migrating an address call; adding the argument label can change its answer.

Through a generic `Sequence` constraint, `contains(_:)` always means exact
element membership. The deprecated direct network overload does not replace
that standard-library contract. The dedicated `addresses` view exposes exact
membership consistently without the legacy overload.

Both network and view customize Swift's
`_customContainsEquatableElement` requirement to answer exact membership in
O(1), including calls through generic `Sequence`, `AnySequence(base)`, and
`.lazy`. This underscored standard-library integration requires validation on
supported Swift toolchains. `contains(where:)` still evaluates its predicate
by iteration. Arbitrary mapping and iterator-closure type erasure can also
lose the fast membership path.

Enumeration remains O(number of addresses). Materializing `Array(network)`,
mapping every address, or reducing the sequence can be impractical even though
membership is constant time. Use a bounded `prefix(_:)` for a sample; use
containment or prefix operations when enumeration is unnecessary.

## Shared CIDR Endpoints

`CIDR.first`, `CIDR.last`, and the endpoints of `CIDR.range` now retain the
receiver's prefix context. This applies consistently to concrete and generic
callers, including `IPAddress`, `IPNetwork`, `CIDRBlock`, and multicast ranges.
`IPPrefix.networkAddress`, `CIDRBlock.firstAddress`/`lastAddress`, and
`AnyIPNetwork.first`/`last` reflect the same change.

```swift
let network = IPv4Network("192.0.2.0/30")!
print(network.first.description) // 192.0.2.0/30
print(network.last.description)  // 192.0.2.3/30
```

`range` remains a `ClosedRange<IPAddress<Family>>`. Its bounds preserve
context, but its membership operation uses `Comparable` ordering and does not
require matching prefix lengths. Use `addresses.contains(_:)` for exact
contextual membership. The existing integer-distance limits of very large
`ClosedRange` traversal also remain; network iteration uses raw storage
arithmetic instead.

`IPAddressRange` and address coverage retain their explicitly raw-bit
semantics. They continue to discard input prefix context and return endpoint
addresses with `/32` or `/128`. CIDRBlock's existing raw address containment
also remains unchanged.

`IPMulticastGroupRange.firstGroup` and `lastGroup` explicitly project endpoint
bits into single multicast destinations. Those typed groups continue to carry
`/32` or `/128`, while the range's shared CIDR endpoints preserve the range
prefix. This projection is necessary because a multicast group initializer
rejects a shorter prefix representing a group range.

## Socket and Consumer Migration

POSIX and SwiftNIO socket identities carry address bits, not CIDR context.
Inbound projections still produce `/32` or `/128`. A consumer that matches a
wire response to a contextual request should compare address bits and retain
the original request value separately; response bytes cannot reconstruct the
request's prefix length.

CIDRNIO's IPv4 projection policy remains unchanged: it rejects the first and
last address of a prefixed IPv4 range. Previously, reading `network.first` or
`network.last` produced `/32` and bypassed that contextual check. Those values
now preserve the parent prefix, so passing them to `makeSocketAddress()` can
throw the existing boundary errors. The current policy also rejects both
boundaries of `/31`. Interior IPv4 addresses and IPv6 projection retain their
existing behavior. Review the application's intended socket policy rather
than discarding context merely to bypass validation.

Consumers that enumerate targets manually from raw integers must supply the
parent prefix explicitly if they want the same context-preserving behavior.
Review address-keyed collections, comparisons with wire-derived host
addresses, and user-visible CIDR text when adopting the migration.

## Prefix Grammar and Address Parsing Policy

All textual prefix lengths now accept only `0` or unpadded ASCII decimal digits
beginning with `1...9`, within the family's range. Forms such as `/00`, `/024`,
`/+24`, and `/-0` are rejected consistently by concrete and generic initializers,
`LosslessStringConvertible`, Codable CIDR strings, Argument Parser, endpoints,
blocks, within-parent construction, and multicast ranges. Standalone
`PrefixLength("024")` and `PrefixLength("+24")` also stop accepting those spellings.
Callers should supply canonical text instead of relying on integer conversion
to normalize it. Numeric initializers retain their range checks.

Standalone `PrefixLength` Codable continues to encode and decode a numeric
scalar. It validates the decoded integer, not the original token spelling:
an underlying decoder may already have normalized numeric `-0` to zero.
CIDR strings inside JSON are subject to the full textual grammar.

`IPAddressParsingPolicy` offers `.compatible` and `.strict`. Existing
initializers, Codable, and CLI parsing select `.compatible`, preserving decimal
interpretation of padded IPv4 octets. Both policies use the same prefix grammar.
The new `init?(_:policy:)` on `IPAddress` and `IPNetwork`, and policy-bearing
initializers on `AnyIPAddress` and `AnyIPNetwork`, allow explicit strict parsing.
AnyIP's parse order remains a performance hint; both family attempts use the
requested policy without a permissive retry.

Strict parsing rejects a multi-digit IPv4 octet beginning with zero, including
IPv4 dotted tails in IPv6. It still accepts valid IPv6 hextet leading zeros,
capitalization, compression, and expanded notation. It does not classify an
address as public, private, or suitable for a particular connection.

Strict callers can compose blocks and endpoints from successfully parsed typed
addresses; their existing text/Codable initializers keep the compatible policy.
No decoder `userInfo` setting or new strict CLI wrapper is introduced.

`IPAddressFamily.parseCIDR(_:requiresPrefix:policy:)` provides one dispatch
requirement for generic and specialized parsing. Existing custom families have
a default compatible implementation using their address-only `parseAddress`
and the shared prefix grammar. The default rejects strict parsing; custom
families must implement the new requirement to support it and honor the same
prefix grammar. `parseAddress` remains address-only.

### Carry Validated Values into Transport

Compatible parsing deliberately preserves registry-ingestion workflows. IANA's
abbreviated padded entries such as `001/8` still require the importing code's
expansion to a four-octet IPv4 address; this patch does not add abbreviated IPv4
syntax to the core parser.

Some system resolvers interpret `012.0.0.1` as octal `10.0.0.1`, whereas compatible
swift-cidr parsing produces decimal `12.0.0.1`. A consumer that validates the
parsed value and then connects using the original string can therefore reach a
different destination. Keep the validated typed address through socket
construction, or pass its canonical `addressLiteral` when text is required.
`description` includes prefix context and is not a bare transport literal.
Typed socket projections retain their existing contextual boundary policy.

The coordinated RouteObjects Ping adapter selects strict IPv4 parsing and rejects
ambiguous numeric input before hostname lookup. Invalid CIDR input is not retried
as a hostname. Valid contextual IPv4 inputs retain their supplied prefix; ordinary
hostnames still resolve through the existing hostname path.

## Dependency Coordination

The coordinated consumer requirement is
`.upToNextMinor(from: "0.8.0")`. A consumer restricted to `0.7.x` will not
automatically adopt this semantic change. During development, validation uses
local editable package overrides. Tracked resolved files must not invent a
`0.8.0` revision before that release exists, and local absolute paths must not
be committed as package dependencies.

After an actual `0.8.0` release is separately approved and published, remove
the development overrides, resolve the coordinated consumer graphs, and
validate their real release pins. The current migration work does not itself
publish or tag that release.
